# Plan 文件規範

在 `req-analysis`、`technical-design`、`gen-task-in-plan` 或
`implementation` 中建立、讀取、拆分或更新 plan 前，先閱讀本文件。
它定義文件組織與正式 plan 項目的溝通方式，
不是另一套生命週期或確認 gate。
各階段所屬的 skill 定義該階段如何討論與確認。

## 單一正式入口

每個 plan 有一份入口文件。使用使用者指定的路徑；
尚未知道位置時，先確認位置再建立。
遵循 repository 的命名與目錄慣例；
`{ticket}_plan.md` 是範例，不是必要名稱。
使用者提供拆分文件時，沿其回連找到入口 plan。
歸屬缺失或模糊時詢問；不要從相似名稱猜測。

依序保留這些頂層章節：

```markdown
# [Plan 標題]

## Req
## Pre Design Sync
## Design
## Task
## Review
## Release
```

逐步建立內容。未來章節可標記尚未開始；
不要為填目錄而製造 Req、決策、Design 或任務。
階段開始時填入既有標題；
不要只因前一個 skill 已建立目錄，就附加重複章節。
各章節包含內嵌正式內容，或有用的摘要與外部正式正文連結，
並在項目存在時附上其權威進度表。
入口 plan 同時是閱讀索引與進度總覽。

## 內嵌或拆分內容

短內容留在檔案內。
某個議題或章節的複雜度、比較、契約或詳細任務，
讓獨立文件更容易 review 時才拆分；
不設固定行數，也不強制拆分。

拆分時：

1. 將詳細正式正文移到一份清楚命名的文件，通常放在 plan 旁。
   保留 ID、已確認結論、條件與含義。
2. 在所屬 plan 章節保留相關摘要、項目 ID／標題，
   以及指向確切正式正文的相對連結。
   DQ 保留精簡結論；Design 保留職責與關鍵邊界；
   Task 保留目的、正式引用與依賴。
   只有「詳見檔案」並不足夠。
3. 外部文件放入回到入口 plan 的連結。
   不維護兩份完整正文或兩份可編輯進度表。
4. 一起更新正文位置與索引。
   每個項目只有一份權威詳細正文；
   變更時，在同次編輯更新受影響摘要。

目的檔案範例包含 `{ticket}_req.md`、`{ticket}_pre_design_sync.md`、
`{ticket}_design.md`、`{ticket}_task.md`、`{ticket}_review.md` 與
`{ticket}_release.md`。
名稱與文件數依變更而定，不是必要集合。

## 權威位置、ID 與狀態

入口 plan 擁有 R／RQ、DQ、D、T／FT、CR 與 RL 項目的進度表。
詳細正式正文在檔案內或索引指定的位置。
完整規格讀正文，狀態讀 plan 表格；
索引摘要永遠不能覆蓋詳細規則。

使用穩定 ID。
後續 DQ／D 群組在索引與引用中明確標示文件／群組時，
可保留局部 ID。
FT ID 跨母 plan 的任務群組指派，
同時檢查既有索引正文與表格；
不要在新檔案產生模糊的重複 FT ID。

共用狀態含義：`Todo` 未開始、`InProgress` 進行中／未完整、
`Review` 可供使用者 review、`Done` 使用者已確認、
`Cancel` 明確取消、`Pending` 明確暫緩。
所屬 skill 控制階段 gate；
`Pending` 不暗示允許跳過阻塞決策。
實作完成停在 `Review`，不能自主驗收為 `Done`。

沿用既有 plan，而表格位於拆分文件時，
將受影響表格移到入口 plan，原位置改為回連。
保留 ID、狀態與結論；
不要遷移無關 plan 或重設已完成工作。
正文／摘要／狀態資訊衝突時提出，
不要默默選擇某個版本。

## 後續工作仍可被找到

同一 Req 下的工作，原始 plan 仍是入口。
後續 Pre Design Sync 與 Design 索引放在原本的對應章節內，
依優化分組並連到其正式正文。
其權威 DQ／D 表格也留在原始 plan。
局部後續設計的 Pre Design Sync 與 Design 放在一起，
不複製整份 Req。

FT 正文索引與進度列放在原始 `## Task` 下，
需要時使用後續工作子章節。
可為可讀性使用獨立 FT 檔，不要求每個小任務都拆檔。
既有 plan 使用 `## Follow-up Task` 時，
將它保留為 Task 的索引延伸，而不是建立第二個狀態權威。
重用已約定的位置；需要新檔案時確認位置。

## Review（試行）

Review 是針對實作所提出之發現的**追溯清單**：發現了什麼、如何判定、
去了哪裡。它不規範修正方式；修正寫在該發現被分派到的 FT、RQ 或 D 項目中。
它的主要價值在於記錄**沒有**產生變更的發現，讓之後的 review 輪次不再重複提出。

本節為試行。下方結構是起點；依實務上 Review 真正需要的內容調整，
並將這些經驗記錄於此。

記錄所有來源的發現：merge 前的 code review（AI 或人工），
以及 QA 或 UAT 期間回報的問題。不要貼上完整的 review 報告。

候選子節；不適用的省略：

| 子節 | 相關內容 |
| :--- | :--- |
| Review 輪次 | 每輪一行：日期、範圍（commit 區間或 Task ID）與來源（AI review、同事、QA、UAT） |
| 發現 | 每個發現一個 `CR01`、`CR02`……：嚴重度、位置、一句話描述、處置與去處 |
| 回饋至慣例 | 選填。當發現的成因是某個 skill 或專案慣例缺漏或錯誤時，註明哪一個應修改 |

每個發現恰有一種處置：

| 處置 | 適用時機 | 去處 |
| :--- | :--- | :--- |
| 修正（Fix） | 實作偏離其 Task、Design 或 Req | 新的 FT |
| 修正規格（Correct specification） | Req、DQ 或 Design 本身錯誤或不完整 | 經 Backward Correction 新增 RQ，再產生新的 T 項目 |
| 刻意設計（Deliberate） | 已有 Pre Design Sync 或 Design 決策涵蓋 | 引用 DQ／D ID；狀態 `Cancel` |
| 接受風險（Accepted risk） | 已知且刻意不處理 | 寫明條件；需要監控時，新增 Release 上線後追蹤項目 |
| 既有問題（Pre-existing） | 基底分支上已存在，且不在本變更範圍內 | 註明負責方或後續單號；狀態 `Pending` |

分派為「修正規格」的發現，依所屬 skill 的 Backward Correction 處理；
在此記錄並不會更新正式基準。

新一輪 review 前，先讀既有發現。已判定為刻意設計、接受風險或既有問題的發現，
除非程式碼或其前提已改變，否則不再提出。

嚴重度使用 🔴 Bug（行為或資料錯誤）、🟡 Risk（目前正確但脆弱）、
🟢 Minor（品質問題，無功能影響）。發現在其去處項目為 `Done`、
或用戶確認其判定時，即為 `Done`。

```markdown
### Review 進度表
| ID | 發現 | 來源 | 嚴重度 | 處置 | 去處 | 狀態 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| CR01 | [發現] | AI review | 🔴 | Correct specification | RQ18, T23 | Done |
```

## Release（試行）

Release 放上線的**執行面**：要做什麼、照什麼順序、在各環境如何確認每一步已完成。
必須成立的約束——部署順序、新舊版本並存、資料準備、過渡機制——
留在 Req 與 Design（Deployment / Transition）；
Release 以 ID 引用它們，不重複其理由。
開關指令、手動觸發重建等操作程序屬於這裡，不寫成 D 項目。

本章節為試行。以下結構是起點；
依實務體會 Release 真正需要什麼來調整，並把這些心得記在這裡。

逐步建立，而不是最後才寫。
任何階段產生上線義務時就加一項：Req 的約束、Design 的順序規則，
或變更快取 key、schema、需要重建的 Task／FT。
合併準備上線前，檢查其完整性。

候選子章節；不適用者省略：

| 子章節 | 相關內容 |
| :--- | :--- |
| 前置條件 | 對其他 repo 或 ticket 的上線依賴、DDL 與資料遷移腳本及其順序、各環境的設定值、外部資源 |
| 操作 | 上線期間使用的指令與手動觸發（開關、重建、快取失效），各自附上如何確認確實完成——不只是呼叫有回應 |
| 步驟 | 各環境依序執行的步驟，每步附正式來源與完成條件；各環境特有的檢查 |
| 回滾 | 資料或程式出錯時怎麼做。若回滾未經推演，明確寫出，而不是暗示它安全 |
| 上線後追蹤 | 監控、重新評估暫緩的任務、移除過渡措施，以及屬於另一張單的工作 |

需要追蹤的項目使用 `RL01`、`RL02`、...。
每個項目要逐環境完成，所以進度表每個環境一個狀態欄；
使用 repository 實際的環境。項目不適用的環境填 `—`：

```markdown
### Release 進度表
| ID | 項目 | SIT | UAT | PROD |
| :--- | :--- | :--- | :--- | :--- |
| RL01 | [Release item] | Todo | Todo | Todo |
```

Release 是輔助判斷的檢查清單，不是照著無腦執行的腳本。
團隊未規定具體測試資料時，驗證步驟可以保持粗略（例如抽查）。

## 讀取、更新與交接

- 從入口 plan 開始並沿相關正式正文連結讀取。
  設計時讀完整適用 Req／AC 與 DQ 正文；
  生成任務時讀完整相關 Design；
  實作時讀指定 Task、依賴、引用的契約／設計與 Validation。
  不要只依摘要工作。
- skill 資源連結相對於 skill 目錄解析，
  專案文件連結相對於所在文件解析，不是 shell 的 cwd。
- 必要正文或連結缺失、無法讀取或矛盾時，
  說明問題並在推進受影響工作前解決。
  不要用探索材料或猜測規格代替。
- 正式 Req、Pre Design Sync 與 Design 不得引用探索材料。
  將必要事實與決定移入自己的正式正文。
  允許連到外部正式正文；這些不是探索檔案。
- 交接入口 plan 路徑、相關 ID 與正文位置。
  狀態只在入口 plan 更新，受影響正文／摘要一起編輯。
  實作提交包含其程式／文件變更與 plan 狀態。

## 決策解釋與變更回報

使用者質疑提案時，解釋決策來源，
不要只說「設計要求如此」。
追查相關正式來源，例如 `T01 ← D02 ← DQ03 ← R04/AC`，
說明哪項需求或已確認決策導致此提案，以及理由。
區分固定需求、已確認技術選擇與新的 AI 建議。
只使用實際項目；不要虛構完整鏈條或從未記錄的理由。
來源缺失或模糊時，明確說明並指出需要釐清的內容。
解釋應自足；不要要求讀探索材料才能理解決策。

提議或套用上游修正時，回報原結論與修訂結論、
變更原因，以及受影響的正式 ID。
指出哪些 DQ、Design 項目、TC 或任務需修改或重新確認，
以及原因，包含狀態變更與從哪個 gate 繼續。
保留無關的已完成工作；
不要默默重設整個階段，或改動多個下游項目卻不解釋影響。
此回報不能代替所屬 skill 要求的使用者確認。

切換階段、呈現階段內容供 review，
或回到上游修正時，簡短標示目前階段。
有幫助時區分需求探索、收斂與 Req review，
以及 Pre Design Sync、Design、Task 生成或實作。
一句自然語言即可；
一般同階段問答不需要重複 `Current Phase` 標頭或任何固定前綴。

`_shared` 是資源目錄，不是 skill：沒有 `SKILL.md`，
也不會自動載入。每個使用它的 skill 都必須明確要求讀取。
