# implementation

專門用於自主執行開發任務的引擎。它能將高階的計畫項目轉換為經過驗證、具備原子化、預先授權提交（atomic, pre-authorized commits）的程式碼變更。

## Plan 入口與 Task 正文

讀取或更新 plan 前，先閱讀
[Plan 文件規範](../_shared/plan-document.md)，
路徑相對於此 skill 目錄解析。
從入口 plan 開始，或沿提供的拆分文件回連找到它。
閱讀每個指定 Task 的完整正文、依賴、適用正式契約／設計與 `Validation`；
不要從索引摘要實作。
權威任務狀態保留在入口 plan，不是在拆分正文。
修改原始碼前，先解決缺失或矛盾的規格。

## 工作流程 (原子化執行循環)

對於每個分配到的 Task ID，此技能必須嚴格遵循以下順序：

1. **上下文與狀態初始化 (Context & Status Initialization)**：
    - **準備狀態**：確認指定任務範圍，以及前置工作已實作並驗證。不要默默增加任務或跳過阻塞依賴。
    - **狀態變更**：將計畫進度表中的 Task 狀態更新為 `InProgress`。**此時先不要進行 commit。**
    - **自動風格注入**：立即調用 `activate_skill("coding-style")` 以載入專案技術棧的相關標準。
2. **實作 (Act)**：
    - 嚴格依照指定正式 Task 正文的「實作細節（Implementation Details）」與適用設計進行程式碼變更。
    - 保持載入的編碼風格中所定義的架構完整性。
3. **驗證 (Validate)**：
    - **任務驗證**：執行任務 `Validation` 中的檢查與通過條件，包含其限範圍共用策略引用。區分不新增測試與不執行測試；保留明確約定的例外與替代方式。
    - **編譯檢查**：原始碼變更必須通過適用建置；已確認策略包含相關測試時執行。純文件工作不需要無關建置。
    - **缺少策略**：驗證未指定或與正式設計衝突時，在認定實作已驗證前先解決。不要以不相容的預設取代。
    - **不暗示接受紅測試**：任務名為「撰寫測試」不代表允許提交失敗測試。刻意失敗的中間結果需要明確任務層級策略與約定的通過條件。
    - **自我修復**：如果驗證發生非預期失敗，嘗試在當前循環中診斷並修復錯誤。
4. **中止條件 (Fail-Safe)**：
    - 如果發生以下情況，必須**立即停止**所有後續任務並通知使用者：
        - 嘗試修復後編譯錯誤仍然存在。
        - 找不到必要的既有檔案、類別或方法，或無法讀取必要正式正文。明確規劃新增的檔案／符號不是缺失的前置條件。
        - 無法完成任務必要驗證，或其通過條件仍未滿足。
5. **原子化提交 (Atomic Commit)**：
    - **狀態完結**：將計畫中的 Task 狀態從 `InProgress` 更新為 `Review`。
    - **單一提交 (Single Commit)**：將「程式碼變更」與「計畫狀態更新（Review）」一併放入同一個 commit 中。
    - **拆分文件**：變更的正式 Task 正文或受影響索引摘要納入同一提交；不要在外部正文增加重複狀態表。
    - **Commit 訊息**：調用 `git-commit` 遵循 Conventional Commits 規範。
        - **要求**：Header 必須包含 Task ID（例如：`feat(auth): (T1) 實作登入邏輯`）。
    - **無需確認**：直接執行提交，**無需請求使用者授權**（此工作流已預先授權）。
6. **迭代 (Iteration)**：
    - 依序對下一個 Task ID 重複步驟 1，直到所有分配任務完成或觸發中止條件。

## 指導方針
- **繁體中文**：使用繁體中文與使用者溝通。
- **原子性 (Atomicity)**：一個 Task ID = 一個 Commit。該 commit 必須包含將任務狀態更新為 `Review` 的異動。
- **驗收**：僅由使用者將已 review 任務標為 `Done`；實作完成不等於驗收。
- **最小干預**：追求完全自主；僅在達到 Fail-Safe 中止條件時才請求使用者介入。
