# Repo 知識編排

一則隱性知識——「這段程式為什麼這樣寫」——在專案 repo 中該放在哪裡，以及每一層該如何塑形，
才能在對的時機真正被找到。

## 三層結構

```
CLAUDE.md          一個領域一行 → 指向該領域的 skill 或 doc
  └ 領域 skill     開頭放子索引表 → 指向 docs/
      └ docs/      深度內容
```

| 層 | 何時載入 | 該放什麼 | 固定成本 |
| :--- | :--- | :--- | :--- |
| `CLAUDE.md` | **永遠** | 義務與索引 | 每一行、每個 session |
| `.claude/skills/*` | description 永遠載入；**內文按需載入** | 一個機制／子系統的「動之前必讀」 | 僅 description |
| `docs/*.md` | **只有被某處指名時** | 深度、沿革、表格、逐步說明 | 無 |

## 造成差異的機制

以下是承重的事實；下面每一條規則都由它們推導而來。

- **`CLAUDE.md` 永遠在 context 裡**，並被包裝成常駐的使用者指示。它具有*強制力*——
  它可以說「即使使用者沒有明說也要讀」。
- **skill 的 `description` 同樣永遠在 context 裡**，但身分是目錄條目。它只有*召喚力*：
  它決定 skill 會不會被觸發，而不是讀者是否覺得受約束。description 裡的命令句
  （「務必」「一律」）不會提高命中率——它是語意比對，不是被遵從的命令。
- **skill 的內文在觸發前不花任何成本。** 所以少而厚優於多而薄：N 個 skill 就是 N 條
  description 在競爭同一次比對，而語意相近的 description 會互相拖累觸發。
- **`docs/*.md` 預設是隱形的。** 沒有任何東西會宣告它的存在。它只能透過 `CLAUDE.md` 的索引行、
  某個指名它的 skill，或明確的 `ls`／`grep` 抵達。它最糟的失敗不是成本——而是**根本沒被發現**。
- **當某件事絕對不能漏時，hook（`UserPromptSubmit`）勝過這三層**：它無條件注入，不依賴模型的
  判斷。代價是每一輪都付全額成本，所以只保留給極少數。

## 每一層該寫什麼

**`CLAUDE.md` — 義務與索引，絕不寫內容。**
每個條目一行，寫*何時該讀*，而不是它裡面有什麼。只有這一層能承載的那句話是
**「即使使用者沒有明說」**。條目以領域為單位、而非以文件為單位：這一層應該隨領域數量成長
（慢），而不是隨檔案數量成長。

> 好：「覺得某段程式邏輯莫名其妙、或不確定某分支還會不會被走到時先查這篇」
> 弱：「主題知識庫，處理相關領域前值得先查」——給不出觸發訊號

**skill 的 `description` — 觸發訊號，不是義務。**
填入真正會出現在提示詞中、或出現在被改動的程式碼中的具體名詞：類別名、欄位名、端點名、
症狀字眼（「某銀行看不到」「退點算錯」）。寫明它*不*涵蓋什麼，以免搶走鄰近 skill 的觸發。

**`docs/` 的檔名 — 檔名就是它的 description。**
那是 `ls` 時唯一看得到的東西。`TapPay請款退款時間序知識庫.md` 找得到；`notes.md` 等同不存在。

## 新知識的路由

1. **有沒有具體的程式碼邊界——「動到 X 之前必須先知道這件事」？**
   沒有（純沿革、某個常數為何是那個數字、哪個分支是死碼）→
   在 repo 的決策／死碼紀錄（`docs/歷史決策與死碼地圖.md` 或同等檔案）追加幾行。結束。
2. **有的話——現有的 skill 是否已經涵蓋那塊程式碼？**
   有 → **加一節進去。不要開新 skill。** 多數事實會落在這裡。
3. **兩者皆非** → 此時才開新 skill，範圍取*一個子系統*、而非*一個事實*，
   讓它有空間吸收同主題接下來的五則發現。

## 領域 skill 的形狀

- **開頭放子索引**——一張「你的問題 → 該讀哪一份」的表——然後把深度推進 `docs/`。
  這正是讓該領域能成長而不必動到 `CLAUDE.md` 的機制。
- **內文記錄*為什麼*，而非*是什麼*。** 程式碼做了什麼從程式碼就讀得到；它為什麼被寫成這樣則不行。
  優先寫理由、規則的來源、與第三方談定的限制、在 UAT 踩到的坑。
- **用類別／方法／欄位名當錨點，絕不用行號。** 行號在下一次編輯就失效；名稱能存活且可被 grep。
  提交前先驗證每個名稱仍然存在。
- **把未經查證的緣由標記為未查證**，而不是杜撰意圖。

## 反模式

| 反模式 | 為何失敗 |
| :--- | :--- |
| 一事一 skill | description 是固定成本且互相競爭；相似的一多就會誤觸發 |
| 純「索引 skill」 | 索引必須在*還不知道主題*時生效；而 skill 只在 description 命中*之後*才觸發，因此來得太晚或根本不來 |
| 把內容（而非索引行）寫進 `CLAUDE.md` | 索引行很便宜，是散文讓它變胖。長了就把散文搬走、保留索引 |
| 把命令句塞進 `description` | 不會提高命中率；義務屬於 `CLAUDE.md` |
| 檔名含糊的 doc | 實務上無法抵達 |

## 把既有的 skill 改成這個形式

1. 把內文拆成*為什麼*（保留）與*程式碼做了什麼*（刪除——那在程式碼裡）。
2. 把冗長的參考材料移進 `docs/`，在 skill 開頭留下一張子索引表。
3. 把 `description` 改寫成觸發訊號；加上「不適用於……」的句子。
4. 把所有行號換成類別／方法名；逐一用 grep 驗證。
5. 確認 `CLAUDE.md` 對該領域恰好有一行，句型是*何時該讀*。
6. 沒有程式碼邊界的內容，改記進決策／死碼紀錄。

## 蒐集仍只存在於人腦中的部分

- 不要安排「找時間寫文件」——那不會發生。把蒐集掛在本來就會發生的工作上：
  code review 時的一句提問、線上問題排查的收尾、新人提問的當下。
- 把收件門檻維持在兩三行——append-only 的清單，不需要結構。
  某個主題累積到數條*且*浮現出明確的程式碼邊界之後，才升級成 skill。
- 讓 AI 當抄寫員：人口述，AI 對照程式碼驗證後成文。
  要求人自己寫 Markdown，通常正是蒐集失敗的原因。
  驗證很重要——回憶常常在欄位數量、名稱、以及哪一方負責計算這些地方，出現細微的錯誤。
