# my-code-review

一個結構化的程式碼審查引擎，用於根據計畫文件驗證實作內容。它採取由上而下（從意圖到細節）的方式，確保實作不僅符合計畫，而且正確、安全且具備可維護性。

---

## 核心原則 (Core Principle)

> **計畫是進入點，而非終點。**

僅符合 Task 檢查清單只能告訴你「做了什麼」。真正的審查在於驗證「是否做得正確且良好」。利用計畫來定位，然後閱讀實際的程式碼，找出計畫無法告訴你的細節。

---

## 工作流程 (Workflow)

一律是「**對整條 feature 分支、對照其基底 (main)** 的多 agent fan-out 審查」。唯一變數是分支有沒有計畫：有計畫就一併對照計畫審（層次 0–2），沒有就純看 code 審（層次 3–6）。

1. **取材（用 git，不透過 PR host）：** `git diff <base>...HEAD`（三點；base 預設 `origin/main`，退而取 `main`）。適用任何 host（GitHub、Gitea、自建）。審已提交的內容，非未提交的零星修改。
2. **偵測計畫：** 自動探測 repo 內的計畫／feature 文件（例如 `docs/` 下的 `plan.md`）——別寫死路徑。
   - **有計畫 → 對照計畫審：** 全部層次適用，含計畫層 0–2。
   - **無計畫 → 純 code 審：** 略過層次 0–2；靠層次 3–6，並從 code＋commit message 推 Design 意圖。
3. **層次 0 由 orchestrator 集中做一次（僅有計畫時）：** 你自己在 fan-out **之前**由上而下讀完計畫——尤其 Pre Design Sync（刻意決策不是 bug）。把相關 Task／Design 片段分給各 subagent，而非讓每個 subagent 各自重讀、各自解讀整份計畫。
4. **Fan-out——唯讀 subagent：** 做完的分支可能動 100+ 檔，別一次審完。把變更檔依 目錄／層／aggregate 分群，每群開一個唯讀 review subagent（上限約 5–6；更多就分批）。每個 subagent：
   - 載入涵蓋其範圍的專案 coding-convention／架構 skill——該 skill 是那些慣例的單一來源，故此處不重述；
   - 對自己那塊套用層次 1–6（層次 1–2 僅在有計畫時）；
   - **讀足夠的周邊脈絡再推理**——別只看 diff，只看 diff 會漏掉深層並發／資料流 bug；
   - 對抗式自我覆核每條 finding，回報 `file:line`＋具體失敗情境＋信心（HIGH/MED/LOW）。
5. **彙整：** 去重成單一報告，並在呈現前對每條 MED 以上／🔴 親自對照 code 覆核。
6. **成本護欄：** diff 非常大時，先回報規模（檔數／粗略 token 量）並確認後再 fan-out。

## 審查層次 (Review Layers)

請依此順序執行審查。每一層都建立在上一層的基礎之上。

### 第 0 層 — 載入上下文 (開始審查前) — *僅對照計畫審時*

> 分支無計畫時，連同第 1–2 層一併略過。有計畫時，由 orchestrator 在 fan-out 前集中做一次（見工作流程）。

**在接觸任何程式碼之前**，請由上而下閱讀計畫文件：

1. **Req** — 了解變更的「原因」。正在解決什麼問題？
2. **Pre Design Sync** — 了解「設計為何如此」。每個 Q 的結論都是深思熟慮的決定。請勿將已記錄的設計決策誤判為 Bug。
3. **Design** — 了解結構與合約應有的樣貌。
4. **Task** — 作為預期變更的檢查清單。

> ⚠️ 跳過 Pre Design Sync 是程式碼審查中最常見的誤判原因。一個看似「錯誤」的設計選擇，往往在 Pre Design Sync 中有記載原因。

---

### 第 1 層 — 完整性 (Task vs 實作) — *僅對照計畫審時*

針對每個 Task 項目，驗證：
- 預期的檔案是否存在且已被修改。
- 新的類別 / 方法 / 欄位是否存在且具備正確的簽署 (Signatures)。
- 新增/移除的相依關係符合計畫。
- 計畫要求的呼叫方已更新（例如：方法簽署變更）。

> 這是檢查清單層次。它是必要的，但並不充足。

---

### 第 2 層 — 意圖對齊 (Design & Req vs 實作) — *僅對照計畫審時*

超越 Task 檢查清單：

- 無論是否遵循確切的 Task 步驟，實作是否滿足 **Req 的驗收標準 (Acceptance Criteria)**？
- 如果實作與 Task 有偏差（例如：將兩個類別合併為一個），請根據 **Design 意圖**而非 Task 的文字描述進行評估。
- 詢問：*這是否達成了 Design 想要實現的目標？*

> 只要滿足 Design 意圖與 Req，與 Task 的偏差**不是 Bug**。反之，如果破壞了 Design 意圖，即使通過了 Task 檢查清單，**仍是 Bug**。

---

### 第 3 層 — 正確性 (閱讀實際程式碼)

驗證實作邏輯本身，獨立於計畫之外：

#### 空值與邊際案例安全性 (Null & Edge Case Safety)
- 所有可為空 (Nullable) 的回傳值在呼叫處是否有防護？
- 快取未命中 (Cache miss) 時會發生什麼？回退 (Fallback) 行為是否正確且符合預期？
- 當集合為空時會發生什麼？

#### 型別一致性 (Type Consistency)
- 各層之間的型別是否一致（例如：DTO 儲存 `int`，handler 比較時也應使用 `int` 而非 enum）？
- 列舉 (Enum) 與整數 (Int) 的轉換是否明確且正確？

#### SQL / 查詢正確性 (如適用)
- JOIN 條件是否正確？
- 欄位別名是否與對應類別的欄位名稱相符？
- 是否正確過濾了軟刪除 (Soft-deleted) 或停用的記錄？

#### 相依關係與 DI
- 新的相依關係是否已在 DI 容器中註冊？
- 是否引入了循環相依 (Circular dependencies)？

---

### 第 4 層 — 影響追蹤 (還有什麼變了)

變更的程式碼會產生漣漪效應。針對每項變更，向外追蹤：

| 變更項目 | 檢查重點 |
| :--- | :--- |
| 方法簽署已變更 | 所有呼叫方都更新了嗎？ |
| 新的建構函式參數 | DI 註冊更新了嗎？ |
| 依賴基底類別行為 | 基底類別對邊際輸入（如 `null`）的實際處理行為為何？ |
| 快取寫入路徑已變更 | 如果寫入的資料是 `null` 會發生什麼？ |
| 發佈了新事件 | 所有訂閱端都能處理新的資料結構嗎？ |

---

### 第 5 層 — 可觀測性 (Observability)

- 重要的失敗路徑是否有記錄日誌 (Log)？
- 快取未命中是無聲的，還是會記錄警告？
- 在生產環境中，是否有方法可以偵測到此程式碼路徑產生了非預期的結果？

> 無聲的回退 (Silent fallbacks) 特別危險：系統看起來運作正常，但回傳了錯誤的資料。

---

### 第 6 層 — 程式碼異味 (Code Smell)

檢查正確性以外的品質問題：

| 異味 | 訊號 |
| :--- | :--- |
| 方法過長 | 一個方法做了太多事情 |
| 邏輯重複 | 同樣的邏輯出現在兩處（這通常是 **Req 的起因**） |
| 抽象層次錯誤 | Handler 在組裝 SQL；Cache 知道 Job 的排程 |
| 建構函式相依過多 | 超過 5–6 個就是一個訊號 |
| 與現有模式不一致 | 新程式碼處理相同關注點的方式與程式庫其餘部分分歧 |

> 請區分**新引入的異味**（必須標註）與**既存的異味**（註記但不應阻擋交付）。

## 輸出格式

分支有計畫時依 **Task** 組織；無計畫時依 **區域／檔案群** 組織。兩者最後都以最終摘要表收尾，並沿用下方嚴重程度。

### 逐項任務摘要 (Per-Task Summary，對照計畫審時)

針對每個 Task ID，輸出一個區塊：

```
### ✅ T1 — [任務名稱]
[用一句話確認已驗證的內容以及通過審查。]

### ⚠️ T3 — [任務名稱]
[一句話摘要。]

#### 問題 1 — [簡短標題]
**嚴重程度：** 🔴 Bug / 🟡 風險 (Risk) / 🟢 輕微 (Minor)
**位置：** `path/to/file.cs` 第 N 行
**描述：** [哪裡錯了以及為何重要]
**建議：** [具體的修正方案或建議]
```

### 無對應 Task／無計畫的變更

做完的分支通常會有沒有對應 Task 的變更——review 中發現的修正、後續重構、順手整理——而無計畫的分支整個都屬此類。**別**因為沒有 Task 就略過。把它們依區域歸類（`非 Task 變更`，完全無計畫時則依檔案群），逐項就層次 3–6（正確性、影響追蹤、可觀測性、code smell）審查，有計畫時再加 Design 意圖。凡是相對 main 改變了對外可觀察行為的，都要標出來，使它是有意識的決定、而非默默漂移。

### 嚴重程度定義

| 等級 | 意義 |
| :--- | :--- |
| 🔴 Bug | 正確性錯誤、資料遺失，或在生產環境中會產生錯誤結果 |
| 🟡 風險 | 目前正確，但結構脆弱，或在邊際案例下會無聲失敗 |
| 輕微 | 程式碼品質、可觀測性或一致性問題，無立即性的功能影響 |

### 最終摘要表

以涵蓋所有 Task 的表格結束：

```markdown
| Task | 狀態 | 備註 |
| :--- | :--- | :--- |
| T1 | ✅ | 正確 |
| T2 | ✅ | 正確 |
| T3 | ⚠️ | 缺失 null guard (🟡) |
| T4 | ✅ | 正確 |
| T5 | ⚠️ | 無 logger，cache miss 靜默 fallback (🟡) |
```

## 指南 (Guidelines)

- **繁體中文**：以繁體中文與使用者溝通。
- **Pre Design Sync 優先**：在報告任何發現前，務必先閱讀 Pre Design Sync。已記錄的設計決策不是 Bug。
- **意圖重於文字**：根據 Design 意圖與 Req 進行評估，而非僅看 Task 步驟。只要保留了意圖，與計畫的偏差是可以接受的。
- **向外追蹤影響**：變更的程式碼行只是起點，而非終點。始終詢問還有什麼可能受影響。
- **區分新舊問題**：明確說明發現的問題是本次變更引入的，還是原本就存在的。
- **不評論風格**：除非違反了已記錄的標準或導致真正的困惑，否則請勿標註格式、命名慣例或個人風格偏好。
