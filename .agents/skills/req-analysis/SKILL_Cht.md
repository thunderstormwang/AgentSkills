# 需求探索與收斂

透過**探索 → 收斂 → Req 確認**，將不完整輸入轉為可信的需求基準。
先查核，再將討論整理成正式範本。此 skill 負責需要什麼與為什麼；
`technical-design` 負責如何滿足已確認的需求。

## 草稿並存

這是供與 `sd-design` 比較的第一版草稿，不是其替代品。
保持既有 skill 與其呼叫端不變。僅在使用者選擇時使用此流程；
不要在同一場討論套用兩套生命週期。
不要在此 skill 下建立 Pre Design Sync、Design、實作任務或原始碼變更。

## 工作文件與正式規格

區分兩種文件：

| 種類 | 目的 | 組織方式 |
| :--- | :--- | :--- |
| 探索材料 | 保存需求原文、查核證據、落差、選項與討論 | 依變更而定；不固定格式、檔案數或必要文件集合 |
| 正式 Req | 陳述完整、已確認的需求基準 | R01–R05 與進度表 |

需求原文、現況查核、落差與待確認等文件是範例，不是必備的三份檔案。
小型討論留在對話或既有材料中；使用者要求，或約定的文件流程需要時才建立檔案。
未指定計畫位置時，先確認儲存位置再建立。

自行判斷探索內容的歸屬，不要請使用者逐項分派討論內容：
原始陳述保存在需求原文材料，已查證行為與證據放在現況查核，
差異、問題、選項與決定放在落差與待確認材料。
其他文件更適合主題時就使用；更新既有材料，不要每輪都建立新檔。
這是內容組織方式，不是固定的必要文件集合。
小型討論仍可只留在對話中。

**正式規格不得引用探索材料。** Req、Pre Design Sync 與 Design 必須包含
各自需要的事實、條件、結論與理由。不要用連結、檔名、章節指向或
「詳見查核」代替內容，即使只是佐證連結也不行。
正式 Req／DQ／D 識別碼可以互相引用；此規則不禁止正式規格之間的追溯。

移入必要的理解，不是整份查核紀錄。
原始查詢、來源摘錄與放棄的選項留在材料中。
材料可以記錄哪個正式項目吸收了結論，使追溯不會讓正式規格依賴材料。

## 1. 先探索，再收斂

1. 保存使用者的需求原文，不要默默改寫其含義。
   區分原文陳述、已查證事實、使用者決定、AI 假設與未解問題。
   假設不是需求。
2. 先從程式、資料與既有文件查核可發現的事實，再請使用者重述。
   遵循 repository 指示並檢查相關路徑，不要從名稱或宣告推論行為。
   無法存取時，明確說明限制；不要將該說法標成已查證。
3. 比較要求的結果與實際行為。依相關性探索術語、受影響使用者與表面、
   邊界、例外、時間行為、相容性、部署義務與驗收期待。
   這些是查核提示，不是文件清單，也不是擴大範圍的邀請。
4. 將可能未說出口的需求提出為問題，並說明其後果。
   詢問預期行為與限制；不要自行增加需求，
   也不要將每個技術實作選擇都變成業務問題。
5. 隨討論演進記錄決定並調整理解。
   有意義的已被取代結論保留在材料中，
   但正式 Req 只承接目前已確認的理解。

重大歧義仍妨礙形成一致 Req 時，留在探索階段。
不要要求使用者事先規定完整文件目錄。
提出有用的組織方式，並於 review 時調整。

### 查核佐證

文件格式自由不代表免除佐證要求。
查核發現不論留在對話或保存於材料，都應記錄以下內容，
讓後續讀者能定位證據並判斷其時效：

- **程式：**相關行為的 repository、檔案路徑，以及實際行號或行號範圍。
  只有類別／方法名稱並不足夠。
  從查閱的原始碼取得位置；不要虛構行號。
- **資料庫查詢或統計：**資料庫環境、查詢日期、SQL 或其他可重現的
  撈取方式，以及實際使用的參數、篩選條件或時間區間。
  包含結果或足夠的統計摘要及其支持的結論；
  只有結論而沒有撈取方式，無法重現。

只保留必要且非敏感的結果細節；不要記錄憑證。
無法取得證據或撈取細節時，說明限制，
不要將缺乏支持的說法呈現為已查證。

### 需求問題

以 `RQ01`、`RQ02`、……標示需要人類確認的需求歧義。
追蹤其背景、行為選項、適當時的建議、結論，以及影響哪些 R 項目。
這可以從材料開始；尚無幫助時，不要強迫建立正式的五項 Req。

若答案須來自 PM、利害關係人或外部團隊，提供可轉寄的 Given/When/Then
釐清草稿，呈現選項差異與確切需要的決定。
這是釐清輔助，不是最終 Acceptance Criteria 的格式。

收斂時，將剩餘 RQ 的必要背景與阻塞影響移入 Req 內的
`### Req 待確認事項`。將已解決的結論移入受影響的 R 項目；
問題紀錄不能代替重寫這些項目。

## 2. 收斂為正式 Req

依已確認理解撰寫 `## Req`：

| ID | 項目 | 內容 |
| :--- | :--- | :--- |
| R01 | Objective | 業務目標與為什麼需要變更 |
| R02 | Current State | 已查證的現有能力與行為 |
| R03 | Proposed Changes | 目標能力、行為變更與相關例外 |
| R04 | Constraints | 不可變更行為、範圍排除、預先決定的選擇、精度／格式與其他固定條件 |
| R05 | Acceptance Criteria | 接受結果的可觀察條件 |

以 PM 與非工程人員可讀的功能語言撰寫 Objective、Current State、
Proposed Changes 與 AC。不放入類別／方法名稱與實作計畫。
技術細節本身是已確認的固定條件時，才屬於 Constraints，
不能只是可能的方案。
探索時發現的設計選擇，除非明確決定為限制，否則仍是設計階段的候選方案。

Current State 包含已查證的現行行為，不是未來意圖或未解猜測。
區分已知缺陷與預期規則；不要默默將缺陷變成保留要求。
若影響範圍，詢問變更應保留或修正該行為。

### Acceptance Criteria

- 使用白話業務規則陳述，不是實作步驟或 Given/When/Then 測試腳本。
  保留精確的業務術語。
- 每個 AC 只處理一個關注點，識別碼如 `AC-{group}-01`；
  無關群組變動時，避免全域重新編號。
- 可觀察的邊界、等號、排序／同值決勝、時間轉換、排除與失敗結果，
  影響需求時都應涵蓋。
- 在相關章節一次陳述共用前提與規則。
  納入其實質內容；不要指回探索材料。
- 未解規則放在 RQ，不是在最終 AC 內放占位文字。
- 區分業務驗收規則與詳細測試案例、具體測試資料、計算過程及斷言。
  當測試屬於驗證策略時，詳細 TC 由設計流程處理。
- 複雜規則可使用獨立的正式 AC 文件。
  它是 Req 的一部分，不是探索材料；保留 R05 為其權威入口。

### 收斂檢查

呈現 Req 供確認前，檢查每個影響需求的材料發現，
是否已納入、明確排除，或記錄為剩餘 RQ。
不要在摘要過程遺失條件。

不開啟材料閱讀正式 Req：讀者能否判定範圍、術語、現行行為、
目標規則、例外、限制與驗收條件？
將缺少的內容寫回 Req。移除材料引用、已解決的暫定措辭，
以及 RQ 結論與 R 項目之間的矛盾。

## 3. 確認與交接

Req 結尾放置自己的進度表：

```markdown
### Req 進度表
| ID | 項目 | 狀態 |
| :--- | :--- | :--- |
| R01 | Objective | Review |
| R02 | Current State | Review |
| R03 | Proposed Changes | Review |
| R04 | Constraints | Review |
| R05 | Acceptance Criteria | Review |
```

這些狀態示範已準備好的草稿，不是預設值。
未開始的內容使用 `Todo`，未完整的內容使用 `InProgress`，
可供確認時使用 `Review`，僅於使用者確認後使用 `Done`。

還有 RQ 時，包含獨立表格：

```markdown
### Req 待確認事項進度表
| ID | 項目 | 結論 | 狀態 |
| :--- | :--- | :--- | :--- |
| RQ01 | [需求問題] |  | Todo |
```

有阻塞 RQ 未解時，不得完成 Req。
`Pending` 僅允許明確非阻塞、且其排除或約定條件已寫在 Req 的項目；
`Cancel` 記錄明確取消的問題。

五個 R 項目都準備好時，請使用者確認完整 Req。
呈現草稿並等待；產出草稿不等於已確認。
review 發現缺少的需求或變更時，回到相關探索與釐清，
重寫受影響的正式 Req 內容，再次等待確認。
確認後，將正式 Req 位置及其已確認範圍、限制與 AC 交給
`technical-design`。探索材料不是必要的交接輸入。
不要僅因最後一題 RQ 已回答就開始設計。

## 向前回溯修正

若後續設計發現真正的範圍、行為、限制或驗收歧義，
在此釐清受影響的 Req 項目。
不要為局部問題重新開始整套需求生命週期。

將新結論記錄在正式 Req，重新評估受影響的正式 DQ、
Design 項目、TC 與任務。
只將需重新確認的依賴項目重設為 `Review` 或 `Todo`，
說明影響，並從修正後的 gate 繼續。
材料可以保留歷史，但只修改材料永遠不會更新正式基準。

以繁體中文溝通並產出專案文件。
