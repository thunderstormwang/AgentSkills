# 任務階段指導方針

這些方針嚴格適用於 `sd-design-helper` 開發生命週期的 **第 4 階段 — Task**。核心目標是產出高品質、可獨立執行的任務清單。

---

## 任務結構與限制 (Task Structure & Constraints)

- **邏輯 Commit 粒度**：每個任務應理想地對應一個邏輯 commit。
- **檔案限制**：每個任務**不得**修改超過 **3 個檔案**。若一個邏輯變更涉及超過 3 個檔案，則**必須**拆分為多個任務。
- **DB Schema 變更**：若涉及 DB 變動，必須建立一個產出 SQL 腳本的任務。
    - **儲存路徑**：腳本必須儲存在專案根目錄的 `sql/` 資料夾中。
    - **檔名格式**：`PXBOX-{jira ticket no}.sql`。
    - **Jira 編號**：若編號不明，必須向使用者確認。
- **API 合約變更**：這是一個**純文件任務**（不涉及任何程式碼變動）。其目的是提供一份清晰、**可直接複製貼上**的摘要給前端同事。
    - **內容要求**：包含 API 路由、變動類型（新增/修改/刪除），以及具體的欄位變動細節。

---

## 任務編排順序建議 (Task Ordering)

為了確保前後端並行開發與整合效率，在產出 Task 清單時應遵循以下順序：

1.  **DB Schema 變更**：優先產出 SQL 腳本。
2.  **Entity / Domain 變更**：定義核心業務邏輯與資料結構。
3.  **API 空殼與欄位**：優先定義 API Request/Response 模型與 Controller 端點。
4.  **API 摘要**：產出給前端同事的 API 變動說明（純文件任務）。
5.  **驗證任務 (Test Task)**：針對功能進入點建立獨立測試任務。此時介面結構已定，必須先撰寫測試定義預期行為（Test-First）。
6.  **詳細功能實作**：實作具體業務邏輯，直到通過驗證任務中的測試。

---

## 內容要求 (Content Requirements)

每個任務的描述必須足夠詳細，使後續執行者無需回頭參考 Design 即可實作。必須包含：

- **引用 (Reference)**：該任務實作的 Design ID。
- **目標專案**：專案名稱或組件名稱。
- **組件 (Component)**：具體的類別名稱。
- **方法 (Methods)**：要新增或修改的方法名稱。
- **邏輯細節**：逐步的邏輯說明、程式碼模式、或具體的驗證規則。
- **測試檔案 (DoD - 僅限測試任務)**：必須明確列出物理測試檔案路徑（如 `src/Project.Test/xxxTest.cs`）。

- **引用**：`[D1]`
- **目標**：`[專案名稱]` -> `[類別名稱]` -> `[方法名稱]`
- **實作細節**：
    - [步驟 1：具體邏輯/指令]
    - [步驟 2：具體邏輯/指令]
- **影響檔案**：(列出所有受影響的檔案，嚴格上限為 3 個)

### T5: Test — [功能名稱] 進入點測試
- **引用**：`[D3]`
- **測試目標**：`[類別名稱]`

- **測試檔案 (DoD)**：`src/PXBox.Spu.Test/Handlers/XxxHandlerTest.cs`
- **影響檔案**：(僅限測試相關檔案，嚴格上限為 3 個)
