# 任務階段指南 (Task Phase Guidelines)

這些指南嚴格適用於 `sd-design-helper` 開發生命週期的 **第四階段 — Task (任務拆解)**。主要目標是產出高品質、可執行的任務，且每個任務都能獨立執行。

---

## 任務結構與限制 (Task Structure & Constraints)

- **邏輯提交粒度：** 理想情況下，每個任務應對應一個邏輯提交 (Commit)。
- **檔案限制：** 預設每個任務涉及的檔案 ≤ 3 個。
    - **精神：** 每個任務必須能獨立 review 且能乾淨 revert。
    - **允許例外：** 機械式變更（rename、enum/const 新增、跨檔同樣 pattern 的編輯）若每個檔案 diff 小（約 < 5 行）且共享同一目的，可超過 3 檔。
    - **不確定時拆細優先** — 拆過頭可救，包太大傷 review。
- **實作程式碼歸於此處：** 所有方法實體、SQL 查詢、對應/組裝邏輯以及其他實作細節必須出現在 Task 階段，而非 Design 階段。Design 僅表達合約（欄位宣告、方法簽署）。
- **資料庫 Schema 變更：** 涉及資料庫變更的任務必須包含產生 SQL 腳本。
    - **儲存：** 儲存至專案根目錄的 `sql/` 資料夾。
    - **檔名：** `PXBOX-{jira ticket no}.sql`。
    - **單號：** 如果不知道 Jira 單號，請詢問使用者確認。
- **API 合約變更：** 這是一個**僅限文件**的任務（不涉及程式碼變更）。其目的是為前端開發人員提供清晰、**可直接複製貼上**的摘要。
    - **內容：** 包含 API 路由、變更類型（新增/修改/刪除）以及 Request/Response 中的具體欄位變更。

---

## 任務排序 (優先順序) (Task Ordering - Prioritization)

產生 Task 列表時，請務必遵循以下順序，以利於並行開發與順暢整合：

1.  **DB Schema 變更**：務必優先產生 SQL 腳本。
2.  **Entity / Domain 變更**：核心業務邏輯與資料結構。
3.  **API 骨架與欄位**：優先定義 Request/Response 模型與 Controller 端點 (Endpoints)。
4.  **API 摘要 (API Summary)**：在定義 API 合約後立即提供前端摘要（僅限文件的任務）。
5.  **驗證任務 (測試任務)**：為進入點建立獨立的測試任務。此時介面已定義；先撰寫測試以定義預期行為（測試先行/失敗先行）。
6.  **功能實作 (Functional Implementation)**：詳細邏輯與優化，持續開發直到測試通過。

---

## 內容要求 (Content Requirements)

每個任務都必須足夠詳細，以便在不參考 Design 章節的情況下即可實作。它**必須**包含：

- **引用 (Reference)：** 此任務實作的 Design ID。
- **依賴 (Dependency)（強制性）：** 列出在此任務之前必須完成的 Task ID（例如：`[Dep: T1, T2]`）。如果沒有依賴關係，請使用 `None`。
- **目標專案 (Target Project)：** 專案/組件 (Assembly) 的名稱。
- **元件 (Component)：** 具體的類別 (Class) 名稱。
- **方法 (Methods)：** 要建立或修改的方法名稱。
- **邏輯詳情：** 逐步邏輯、程式碼模式或具體的驗證規則。
- **測試檔案 (DoD - 僅限測試任務)：** 必須指定實體測試檔案路徑（例如：`src/Project.Test/xxxTest.cs`）。
