# task-acceptance

這是使用者原本在實作者完成後要親手做的每批 review：**它有沒有照每個任務說的做？** 目的是幫使用者省下回答這個問題的時間，讓使用者只在真正需要判斷的地方才去看。

實作者的報告是**一個說法，不是證據**。這個技能之所以存在，是因為實作者檢查自己並不獨立——這裡的每個結論都必須來自 repository，而不是來自報告。

## 範圍

| 範圍內 | 範圍外 |
| :--- | :--- |
| subagent 在這一批實作並 commit 的任務 | 調查／review subagent 的發現（照常抽查即可） |
| 是否符合每個任務的正式內文，並經由它符合計畫 | 整個計畫／整個分支的 review——由使用者主導；請用 `branch-review` |
| 代表使用者將通過驗收的任務標為 `Done` | 修正程式——退回給實作者，或詢問使用者 |

呼叫這個技能，就是使用者委託了每批的驗收。如果使用者表示某一批要自己 review，就在摘要之後停下，狀態維持在 `Review`。

## 輸入

開始檢查前，先備妥：

- 實作者的報告（commit SHA、偏離、不確定之處、被修改的斷言、測試數字）。
- 入口計畫，以及這一批每個任務的**完整正式內文**（Current state / Goal / Implementation Details / Validation / Test File / Affected Files），依 [Plan Document Conventions](../_shared/plan-document.md) 追蹤拆分文件的連結。絕不以索引摘要作為驗收依據。
- 這一批之前的測試基準，若派工時有記錄的話。

## 檢查

依變更的規模調整投入：只改文件的任務只需要檢查 1、6、7。

1. **Repository 狀態** — 目前分支是預期的分支；工作區乾淨；每個回報的 SHA 都存在、一個任務一個 commit，且各自包含計畫狀態改為 `Review` 的異動；沒有 push；範圍內沒有未回報的 commit。
2. **重新建置並跑全部測試** — 先重新建置，再跑整個測試套件（絕不使用 `--no-build` 之類的捷徑；實作者的二進位檔可能是舊的）。將數字與基準、與報告比對。
3. **任務符合度** — 核心檢查。對每個任務，以正式內文對照其 commit 的 diff（先看正式程式）：
   - 實作細節的每一項都存在於這一批的最終狀態；
   - 沒有改動任務範圍以外的東西；
   - 任務的 Validation 真的有達成，且 Test File (DoD) 存在；
   - Affected Files 相符；任何多出或缺少的檔案都有說明。
4. **被修改的既有斷言** — 列出這一批修改或移除的每一個既有測試斷言。每一處都必須能追溯到任務所規定的行為變更。沒有說明的修改是讓測試通過最便宜的方法，不得默默接受。
5. **殘留** — 對任務規定的改名與移除，搜尋舊名稱在該消失的地方已消失。
6. **報告中的說法** — 驗證實作者列出的每一個偏離與「不確定」項目，並找出它沒有列出的偏離。
7. **狀態** — 交回時任務是 `Review`，絕不是 `Done`。

## 為每個任務分類

| 類別 | 意義 | 狀態 |
| :--- | :--- | :--- |
| **A — 符合** | 照任務說的做完；沒有發現問題 | `Done` |
| **B — 有偏離，但仍符合計畫** | 與任務的字面不同，但任務要求的行為以及計畫的 Req/Design 仍然成立（例如多一個測試 helper 參數、更清楚的命名、等價的結構） | `Done` |
| **C — 需要使用者** | 任何改變行為、契約、資料或測試意義的偏離；沒有任務規定理由的斷言修改；Validation 未達成；或任何你無法驗證的事 | 維持 `Review` |

在 B 與 C 之間不確定時，選 C。錯判成 C 只花使用者看一眼；錯判成 B 會把問題藏到整個計畫的 review 才浮現。

## 套用與回報

1. 在入口計畫的進度表中將 A 與 B 任務設為 `Done`（只改狀態欄），並以 `git-commit` 技能將這個變更獨立成一個 commit。C 任務維持在 `Review`。不要 amend 或 squash 實作者的 commit。
2. 用繁體中文給使用者一份簡短摘要：
   - 每個任務一行：類別，以及簡短的原因；
   - B：與任務哪裡不同，以及為什麼仍符合計畫；
   - C：使用者具體該確認什麼，附 `file:line`；
   - 你自己驗證了什麼（建置結果、測試數字前 → 後），與任何未經驗證、轉述自實作者報告的內容分開。

保持簡短。這份摘要取代使用者的每批 review；它不應該比直接讀 diff 還長。
