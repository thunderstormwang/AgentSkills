# 已確認 Req 下的技術設計

依已確認的需求基準產出 **Pre Design Sync → Design**。
先定案技術選擇，再規定設計；使用者確認後才交給
`gen-task-in-plan`。此 skill 不生成實作任務或原始碼變更。

## Plan 入口與入口 Gate

讀取、建立或更新 plan 前，先閱讀
[Plan 文件規範](../_shared/plan-document.md)，
路徑相對於此 skill 目錄解析。
從入口 plan 開始並沿正式正文連結讀取；
不要從索引摘要推論完整需求。

1. 閱讀正式 Req，包含限制、AC、未結 RQ 與實際確認狀態。
   不要從檔案存在或最後一題已回答推論已確認。
2. 僅在 R01–R05 已確認且無阻塞需求歧義時開始 Pre Design Sync。
   否則將受影響問題交給 `req-analysis`，不要自行製造缺少的業務規則。
3. 其他流程產出的已確認 Req 也是有效輸入。
   不要要求以 `req-analysis` 重新建立。
4. Pre Design Sync 與 Design 的索引保留在入口 plan。
   正文可內嵌或使用已約定的拆分文件。
   後續工作從原始 plan 連到局部設計；
   DQ／D 進度表保留在該 plan。
   未指定新的正文位置時，先確認位置。

### 後續優化

對已實作 plan 的較大優化，繼承其已確認 Req 並檢查相容性。
不要只為開始優化而重新生成五項 R、重新確認整份 Req，
或重設已完成階段。

記錄正式基準引用，以及理解此局部設計所需的相關範圍、限制與 AC 條件。
將局部 Pre Design Sync 與 Design 放在一起。
前次任務的「本次不做」不自動成為 plan 全域禁止；
應與原始 Req 區分。
保留已接受風險與其條件，不要自動增加補償或重播工作。

生成 FT 任務前先討論做法。
簡單更名、註解與直接的後續工作可直接交給 `gen-task-in-plan`；
不是每個 FT 都需要獨立設計討論。

## 正式文件不得依賴探索材料

Req、Pre Design Sync 與 Design 不得引用需求原文、
現況查核、落差與待確認或其他探索材料。
不要放連結、檔案／章節指向或「詳見查核」，即使是佐證也不行。
將必要的已查證事實、條件、決定與理由直接納入需要它們的正式章節。

針對每個相關議題查核現行程式；
Req 描述業務行為，不是現行實作結構。
材料可以協助定位證據，但需要時應重新查證，
不要把舊觀察當成現行事實。
不要將完整討論紀錄或原始查詢貼入正式設計。

正式 Req、DQ、D、AC、TC 與 Task 項目之間仍可互相引用。
也允許獨立的正式 Pre Design Sync 或 Design 文件；
它們是規格的一部分，不是探索材料。
拆分時保留權威識別碼、結論、狀態與確認 gate。
不要只是為了符合行數而拆分。

## 1. Pre Design Sync

在入口 plan 的 `## Pre Design Sync` 填入影響架構、歸屬、資料模型、快取、
契約或整合的未解技術選擇。
每個決策使用一個 `DQ01`、`DQ02`、……。尚不要產出 Design 章節。

對每個 DQ：

1. 陳述決策、相關已查證實作事實與限制。
   納入足夠背景，使讀者不讀探索材料也能理解。
2. 有多個候選方案時，提供比較表，涵蓋做法、優缺點、變更範圍與風險。
   明確寫出建議方案與理由；不要只留下未排序清單給使用者。
3. 請使用者決定。在詳細正文與入口 plan 的進度表記錄最終結論；
   精簡表格不能代替決策必要的條件或理由。
4. 檢查結論是否符合 Req 與已解決的 DQ。
   真正衝突應提出由使用者解決，而不是默默選擇其中一方。

範圍、預期行為、術語與驗收歧義屬於 Req，不是 DQ。
停止受影響的設計工作並將這類問題交回 `req-analysis`；
修正的需求確認後再繼續。

```markdown
### Pre Design Sync 進度表
| ID | 項目 | 結論 | 狀態 |
| :--- | :--- | :--- | :--- |
| DQ01 | [設計決策] |  | Todo |
```

未解決的決策使用 `Todo`／`InProgress`，
提議結論待確認使用 `Review`，使用者確認的結論使用 `Done`。
明確取消的項目使用 `Cancel`。
`Pending` 只有明確非阻塞、且已記錄排除或約定條件時才能通過 gate；
不能藏住設計所需卻未決定的輸入。

所有 DQ 都是 `Done`、`Cancel` 或明確非阻塞的 `Pending` 後才繼續。
若沒有未解技術選擇，記錄該階段沒有 DQ 的原因；
不要為填範本而製造問題。

## 2. Design

在入口 plan 的 Pre Design Sync 後填入 `## Design`，不要移除或覆寫其決策。
定義結構與行為契約：改什麼、責任放哪裡，
以及必須成立的順序／不變量。

依已確認決策與實際變更提出有用章節。
使用者不必先規定完整目錄。
review 時新增、移除或調整章節；以下主題是候選項目，不是必備交付物。
省略不能隱藏相關契約、併發、失敗處理或驗證議題。

| 候選主題 | 相關內容 |
| :--- | :--- |
| Impact Scope | 受影響服務、API 與既有行為 |
| DB Schema | 資料表、欄位、精度、索引、既有資料遷移與初始化 |
| Domain Model | Entity、Value Object、Enum、關係與不變量 |
| Contracts | API 請求／回應、事件形狀、相容性與消費端 |
| Caching Strategy | Key、資料結構、TTL、一致性、介面與失效 |
| Internal Component Structure | 職責、依賴、DI 邊界、簽名、搬移或移除的行為 |
| Core Logic Spec | 行為規則、優先序、早退、順序、狀態轉換、併發與失敗處理 |
| Component Flow | 有用的呼叫／副作用順序，可選擇搭配圖表 |
| Deployment / Transition | 必要部署順序、共存、資料準備與已接受的切換風險 |
| Validation Strategy | 適用的建置、測試、review，以及約定的限範圍例外或替代方式 |
| Test Plan | 新增或修改測試時的目標、框架、檔案與正式 TC 入口 |

歸屬與依賴決策放在 Internal Component Structure；
行為規則放在 Core Logic Spec。
交叉引用正式項目，不要重複兩邊內容。
Domain Model 不是裝所有服務介面或流程編排的容器。

Component Flow 圖表適用於釐清順序或合作，
不是每份設計都必備。
此次討論移除圖表，不代表禁止後續變更使用。

**僅限契約的程式片段：** 允許欄位宣告、方法簽名與事件形狀。
方法本文、可執行 SQL 查詢、映射／組裝程式屬於 Task，不是 Design。
以文字規定遷移範圍與必要效果，不撰寫實作 SQL。

### Validation Strategy 與 Test Plan

提出適當驗證並記錄已確認策略。
區分「不新增測試」與「不執行測試」；
每項例外只限授權工作，並保留適用替代方式。
不得將任何一項解讀為不用驗證或整個 repository 的豁免。

新增或修改測試時，將詳細 TC 放在獨立的正式
`{ticket}_tc.md` 或適當的分層 TC 文件。
Design 的 Test Plan 包含目標、框架、測試檔案路徑與 TC 連結。
Req AC 不需要反向 TC 連結。

TC 指引：

- 引用對應正式 AC ID，使用具體 Given/When/Then 值。
  避免 `$X`、「視設定而定」或未指定的預期輸出；
  拆成具體案例。
- 標題使用如 `{MethodUnderTest}_{Scenario}_{ExpectedBehavior}`，
  每個標題下放一行繁體中文描述。
- 包含術語與可觀察輸出欄位對照，讓測試作者能識別正確斷言。
- 涵蓋相關邊界、失敗路徑、順序與受變更影響的既有共用行為，
  不只是新的正常路徑。
- 檢查 TC 是否符合已確認 AC 與 Design。
  修正謄寫不一致；真正規格歧義交回 Req，不要自行製造規則。

不適用新增／修改測試，或明確排除時，
省略不必要的 Test Plan／TC 產物，但保留 Validation Strategy。

### Design 確認

實際設計章節使用 `D01`、`D02`、……，
入口 plan 的 Design 章節以此表結尾，即使正文拆分也一樣：

```markdown
### Design 進度表
| ID | 項目 | 狀態 |
| :--- | :--- | :--- |
| D01 | [設計章節] | Review |
```

未完整章節使用 `Todo`／`InProgress`，
準備好供確認時使用 `Review`，使用者確認後才使用 `Done`。
`Cancel` 與 `Pending` 與 Pre Design Sync 一樣，
須有明確、非阻塞的意義。

呈現前，檢查 Design 是否符合 Req、DQ 結論、其他 D 項目與 TC。
通知前先修正謄寫錯誤。
提出實質衝突與需要使用者決定的選擇；
不要默默改變已確認決策。

## 3. 交接與向前回溯修正

每個 D 項目都已確認或明確非阻塞／取消後，交給
`gen-task-in-plan`：初始任務用 Mode A，後續任務用 Mode B。
提供入口 plan 與正式 Req／設計正文位置、適用 DQ／D ID、依賴、
限制、已接受風險條件與驗證策略。
不要在此 gate 前生成任務，也不要要求探索材料才能實作。

上游結論改變時，追溯最早的正式來源：
`Task ← D ← DQ ← Req/AC`。修正它並重新評估依賴項目。
只將受影響且需重新確認的項目重設為 `Review` 或 `Todo`；
不要重設無關的已完成工作。
只更新探索材料永遠不會更新正式決策。

以繁體中文溝通並產出專案文件。
